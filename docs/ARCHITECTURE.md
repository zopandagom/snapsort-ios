# 아키텍처

두 가지 결정 위에 서 있다.

1. **규칙 기반 단방향 MV.** SwiftUI 의 `@Observable` 모델을 View 에 직접 연결한다(Apple 샘플과 같은 방식). 단방향 흐름은 프레임워크가 아니라 규칙과 lint 로 강제한다.
2. **모듈러 아키텍처.** 외부 시스템은 Client 모듈로 감싸고, 각 Client 를 Interface / Impl / Testing 으로 나눈다. Feature 는 Interface 에만 의존한다.

## 1. 실행 흐름

```mermaid
flowchart TD
    View["View<br/>state 를 읽어 렌더링만"]
    Model["Model (@Observable @MainActor)<br/>private(set) 상태 · 이벤트 메서드"]
    Client["Client protocol (Sendable)<br/>*Interface 모듈"]
    Impl["Impl<br/>PhotoKit · Vision · FoundationModels · SwiftData"]
    Fake["Fake<br/>*Testing 모듈 · 테스트/Example"]

    View -- "① 이벤트: model.startButtonTapped()" --> Model
    Model -- "② async 호출" --> Client
    Client -. App 이 주입 .-> Impl
    Client -. 테스트가 주입 .-> Fake
    Client -- "Sendable 값 반환" --> Model
    Model -- "③ 상태 변경 → ④ Observation 이 re-render" --> View
```

### 단방향 규칙
| # | 규칙 | lint 로 강제 |
|---|---|---|
| 1 | Model 의 상태 프로퍼티는 모두 `public private(set) var` | 리뷰 |
| 2 | View 는 Model 의 **이벤트 메서드**만 호출한다. 이름은 "무슨 일이 일어났는가"로 짓는다: `onAppear()`, `startButtonTapped()`, `queryChanged(_:)` | 리뷰 |
| 3 | 입력 컨트롤은 `Binding(get: { model.query }, set: { model.queryChanged($0) })` 으로 연결한다. `$model.query` 금지 | `no_two_way_model_binding` |
| 4 | 부수효과(권한, OCR, 저장, 알림)는 Model 메서드 안에서 Client 를 통해서만 실행한다. View 에서 `Task { PHPhotoLibrary… }` 금지 | `system_framework_only_in_impl` |
| 5 | Model 은 `@MainActor`, Client 가 주고받는 값은 `Sendable`. `PHAsset` 같은 비 Sendable 객체는 식별자나 Core 의 `Sendable` 값 타입(예: `ImageAsset`)으로 바꿔서 넘긴다 | 컴파일러 (Swift 6 strict) |
| 6 | Model 끼리 직접 참조하지 않는다. 화면 간 흐름은 App 이 조립하거나 공유 Client 를 거친다. 같은 Feature 안 화면 사이의 신호는 그 Feature 의 View 가 한 Model 의 상태 변화를 다른 Model 의 이벤트로 넘긴다(예: `LibraryView` 가 `onChange(of: storeRevision)` 로 `CategoryModel.libraryStoreChanged()` 를, `onChange(of: usageRevision)` 로 `LibraryModel.gifticonUsageChanged()` 를 부른다) | 모듈 경계 (같은 Feature 안 View 전달은 리뷰) |
| 7 | Model 은 App(또는 Example 앱)이 `@State` 로 **소유**하고, View 는 `let model: XxxModel` 로 **참조**만 한다. View 안에서 Model 을 생성하거나 `@State` 로 다시 감싸지 않는다 | 리뷰 |
| 8 | View 전용 일시 상태(애니메이션, 포커스, 시트 표시 여부)는 View 의 `@State private var` 로 둬도 된다. 화면에만 걸린 시스템 UI 설정(예: 기록 중 자동 잠금 끄기 `isIdleTimerDisabled`, 바코드 크게 보기의 화면 밝기 최대 — 나가거나 앱이 뒤로 가면 되돌린다)도 View 가 맡는다. 저장·외부로 남지 않고 화면을 떠나면 되돌리므로 규칙 4 의 부수효과가 아니다. 비즈니스 의미가 있으면 Model 로 옮긴다 | 리뷰 |

### 예시 (OnboardingFeature)
```swift
@MainActor
@Observable
public final class OnboardingModel {
  public private(set) var access: PhotoAccessState

  @ObservationIgnored private let photoLibrary: any PhotoLibraryClient

  public func startButtonTapped() async {
    self.access = await self.photoLibrary.requestAccess()
  }
}

// View
Button("정리 시작하기") { Task { await self.model.startButtonTapped() } }

// App: 화면 간 흐름은 App 이 정한다 (규칙 6)
if self.onboardingModel.access.canRead {
  LibraryView(
    model: self.libraryModel,
    categoryModel: self.categoryModel,
    gifticonListModel: self.gifticonListModel,
    receiptListModel: self.receiptListModel,
    captureActionsModel: self.captureActionsModel,
    tripListModel: self.tripListModel,
    tripDetailModel: self.tripDetailModel
  )
} else {
  OnboardingView(model: self.onboardingModel)
}
```

## 2. 모듈 구조

```mermaid
flowchart TD
    App["App (SnapSort)<br/>조립 지점"]
    Widget["Widget extension (W4)<br/>저장소 Client Interface 만 의존"]
    subgraph Features
      Library["LibraryFeature"]
      Other["…Feature"]
    end
    subgraph Clients
      PI["PhotoLibraryInterface"]
      PImpl["PhotoLibraryImpl"]
      PT["PhotoLibraryTesting"]
    end
    subgraph Shared
      Core["Core<br/>도메인 값 타입·규칙"]
      DS["DesignSystem<br/>공용 UI"]
    end

    App --> Library & Other
    App --> PImpl
    Library --> PI
    Library --> DS
    PImpl --> PI
    PT --> PI
    Library & PI & PImpl --> Core
```

### 모듈 종류와 타깃
| 종류 | 위치 | 타깃 | 역할 |
|---|---|---|---|
| App | `Projects/App` | `SnapSort` | 유일한 조립 지점. Impl 을 생성해 Model 에 주입 |
| Feature | `Projects/Features/<Name>` | `<Name>Feature` · `<Name>FeatureTests` · `<Name>FeatureExample` | 화면 하나 또는 흐름 하나. Model + View |
| Client | `Projects/Clients/<Name>` | `<Name>Interface` · `<Name>Impl` · `<Name>Testing` · `<Name>Tests` | 외부 시스템 경계 |
| Shared | `Projects/Shared/<Name>` | `<Name>` · `<Name>Tests` | 여러 모듈이 함께 쓰는 코드. `Core`(도메인 값 타입·규칙), `DesignSystem`(공용 UI: 썸네일 칸·격자 열·상태 안내·CGImage 방향 변환) |

- **Interface**: 프로토콜과 값 타입(`PhotoAccessState` 등)만. Apple 데이터 프레임워크와 CoreLocation·MapKit 을 import 하지 않는다.
- **Impl**: 프로토콜 구현. 구현 타입 이름은 `<Name>ClientImpl`. Apple 데이터 프레임워크(Photos·Vision·FoundationModels·SwiftData·StoreKit·UserNotifications) import 는 여기서만. 예외: Feature View 의 MapKit `Map` 렌더링(§4). 이 목록과 CoreLocation·MapKit(§4 경계) 밖의 iOS 프레임워크(CoreGraphics·ImageIO 등)는 Core 를 포함한 모든 레이어에서 쓸 수 있다. 제한은 권한·저장·외부 서비스 같은 부수효과를 Impl 에 가두기 위한 것이므로, 부수효과 없는 프레임워크를 피하려고 실행 비용을 들이지 않는다.
- **Testing**: `<Name>ClientFake`. 고정 값을 돌려주는 `struct` 로 시작하고, 호출 기록이 필요하거나 호출 사이에 상태가 남아야 하면(저장 결과, 바뀐 권한) 그때 상태를 `Mutex` 로 보호하는 `final class` 로 확장한다.
- **Example**: Fake 로 Feature 를 단독 실행하는 데모 앱. **`#Preview` 도 여기에 둔다** (Feature 모듈이 Testing 에 의존하지 않도록).
- **Debug 전용 Feature**(SampleRecorder): Sources 의 모든 파일을 `#if DEBUG` 로 감싸고 App 도 `#if DEBUG` 에서만 연결해 Release 에 들어가지 않는다(Tuist 의존성은 구성별로 나눌 수 없어 Release 에서는 빈 모듈을 링크한다). 확인은 `SnapSort` 스킴을 Release 구성으로 빌드해 앱 바이너리에 `SampleRecorder` 심볼이 없는지 본다(`make project` 뒤 `xcodebuild build -workspace SnapSort.xcworkspace -scheme SnapSort -configuration Release -destination 'generic/platform=iOS Simulator' -derivedDataPath build/ReleaseDD CODE_SIGNING_ALLOWED=NO -quiet && nm build/ReleaseDD/Build/Products/Release-iphonesimulator/SnapSort.app/SnapSort > build/release-symbols.txt && ! grep -q SampleRecorder build/release-symbols.txt && echo "기록 도구 없음"` 이 "기록 도구 없음"을 출력하면 통과. 빌드·`nm` 중 하나라도 실패하면 출력이 없도록 `&&` 로 잇고 개수가 아니라 이 문구로 판정한다). 기록 도구 Sources(`Projects/Features/SampleRecorder/Sources`)나 App(`Projects/App`)을 바꾼 작업에서 Claude 가 수용 확인(CONVENTIONS §6)으로 실행한다. Example 앱은 Debug 로만 빌드하므로 모든 타깃을 담은 `SnapSort-Workspace` 스킴은 Release 로 빌드되지 않는다.
- **Shared**: Apple 데이터 프레임워크, CoreLocation·MapKit, Client 모듈을 import 하지 않는다. Core 는 부수효과 없는 순수 코드이고(SwiftUI·UIKit 도 쓰지 않는다. lint `core_no_ui_framework`), 좌표·분석 이미지처럼 여러 Client 의 Interface 가 함께 쓰는 값 타입을 둔다. DesignSystem 은 SwiftUI 까지 쓴다. 다른 Shared(Core)에 의존하지 않으므로 이미지는 CoreGraphics 값(CGImage·방향)으로 받는다.

### 의존 규칙
| from ↓ / to → | Feature | Interface | Impl | Testing | Shared |
|---|---|---|---|---|---|
| App | ✅ | ✅ | ✅ | ❌ | ✅ |
| Feature | ❌ | ✅ | ❌ | ❌ | ✅ |
| Feature Tests / Example | 자기 Feature | ✅ | ❌ | ✅ | ✅ |
| Client Interface | ❌ | ❌ | ❌ | ❌ | ✅ |
| Client Impl | ❌ | 자기 Interface (+ 다른 Interface) | ❌ | ❌ | ✅ |
| Client Tests | ❌ | ✅ | 자기 Impl | 자기 Testing (+ Impl 이 쓰는 다른 Client 의 Testing) | ✅ |
| Shared | ❌ | ❌ | ❌ | ❌ | ❌ (필요해지면 템플릿에 인자를 추가하고 연다) |

### 빌드 설정
- 모든 모듈은 static framework. iPhone 전용, iOS 26.0+, Swift 6 언어 모드, `SWIFT_STRICT_CONCURRENCY=complete`.
- 설정은 `Tuist/ProjectDescriptionHelpers/Project+Templates.swift` 의 `Env` 에서만 바꾼다. 개별 매니페스트에서 덮어쓰지 않는다.
- 서명: 모든 타깃이 Xcode 자동 서명(`CODE_SIGN_STYLE=Automatic`)과 `Env.developmentTeam` 팀을 쓴다. 실기기 빌드는 Xcode 가 인증서·프로파일을 관리하고, `make build`/`make test` 와 CI 는 `CODE_SIGNING_ALLOWED=NO` 로 서명 없이 빌드한다.
- 타깃 소스·리소스는 Xcode 동기화 폴더(`buildableFolders`)로 연결한다. 기존 폴더 안에서 파일을 추가·삭제하면 다시 생성하지 않아도 Xcode 와 빌드에 반영된다. 모듈·타깃·의존성을 바꿀 때만 `make project` 를 다시 돌린다.

## 3. 모듈 추가 방법

### Client 추가 (예: ImageAnalysis)
1. `Tuist/ProjectDescriptionHelpers/Module.swift` 의 `Client` 에 `case imageAnalysis = "ImageAnalysis"` 추가.
2. 디렉터리 생성: `Projects/Clients/ImageAnalysis/{Interface,Impl,Testing,Tests}` + `Project.swift`:
   ```swift
   import ProjectDescription
   import ProjectDescriptionHelpers

   let project = Project.client(.imageAnalysis, shared: [.core])
   ```
   Impl 이 다른 Client 를 조합하면(예: Indexing) `clients: [.photoLibrary, …]` 를 더한다. Impl 에는 그 Interface 가, Tests 에는 Interface 와 Testing(Fake)이 연결된다.
3. Interface 에 `public protocol ImageAnalysisClient: Sendable` 과 입출력 값 타입, Impl 에 `ImageAnalysisClientImpl`, Testing 에 `ImageAnalysisClientFake`, Tests 에 Impl 의 순수 로직 테스트.
4. 사용하는 Feature 매니페스트의 `clients:` 에 추가하고, App 매니페스트에 `.client(impl: .imageAnalysis)` 추가.
5. `make project && make test`.

### Shared 추가 (예: Core)
1. `Module.swift` 의 `Shared` 에 `case core = "Core"` 추가.
2. `Projects/Shared/Core/{Sources,Tests}` + `Project.swift`:
   ```swift
   let project = Project.shared(.core)
   ```
3. 쓰는 모듈의 매니페스트에 연결한다: Feature 는 `Project.feature(_, clients:, shared: [.core])`, Client 는 `Project.client(_, shared: [.core])`, App 은 `dependencies` 에 `.shared(.core)`.
   DesignSystem 같은 공용 UI 모듈은 Feature 와 App 에서만 쓴다 (Interface 는 프로토콜과 값 타입만).

### Feature 추가 (예: Onboarding)
1. `Feature` 에 `case onboarding = "Onboarding"` 추가.
2. `Projects/Features/Onboarding/{Sources,Tests,Example}` + `Project.swift`:
   ```swift
   let project = Project.feature(.onboarding, clients: [.photoLibrary])
   ```
3. `Sources` 에 `OnboardingModel`, `OnboardingView`. `Tests` 에 Model 테스트. `Example` 에 `@main` 데모 앱과 `#Preview`.
4. App 매니페스트 dependencies 에 `.feature(.onboarding)` 추가, `SnapSortApp` 에서 Model 을 만들어 연결.

## 4. 확정된 기술 결정
| 결정 | 이유 |
|---|---|
| 서버 없음 | "사진이 밖으로 나가지 않는다"가 제품 가치. StoreKit 2 는 기기에서 영수증 검증 |
| 위치·지도는 Apple 시스템 서비스 | 장소 이름 변환은 MapKit `MKReverseGeocodingRequest`(`CLGeocoder` 는 iOS 26 에서 deprecated. 요청 수 제한이 있으므로 사진마다가 아니라 위치 묶음마다), 지도 핀은 MapKit `Map`(여행 폴더 상세를 열 때만 반올림 중심점 핀 하나를 보이는 고정 지도. 사진마다 핀을 꽂지 않는다. Feature 에서 MapKit 을 import 하는 파일은 LibraryFeature `TripMapView` 하나다. 지도 타일 요청은 CLAUDE.md 의 "지도 표시" 예외다). 모듈 경계: ① Feature View 는 `Map` 렌더링만을 위해 MapKit 을 import 할 수 있다 ② 지오코딩과 지도 앱 열기는 부수효과이므로 Client Impl 에서 한다(Map Client. `MapClient.openInMaps(address:)` 는 주소 문자열을 지도 앱 검색 `maps://?q=`(RFC 3986 unreserved 밖은 모두 퍼센트 인코딩)으로 넘기기만 하고 앱은 주소를 지오코딩하지 않는다. 지도 앱이 그 주소를 검색하는지는 실기기에서 확인한다. 역지오코딩은 `MapClient.placeName(near:locale:)` 하나로, Core `RoundedCoordinate`(반올림 좌표 ×100 정수 두 개)를 받아 `PlaceInfo`(이름·시간대 식별자)를 돌려준다. Impl 은 그 정수에서 만든 좌표만 `MKReverseGeocodingRequest` 에 넣고 `preferredLocale` 을 넘긴 로캘로 둔다. 이름은 응답 항목의 `addressRepresentations` 에서 cityWithContext → cityName → regionName 중 앞뒤 공백을 지우고 비지 않은 첫 값이다(실측: 제주 "제주특별자치도 제주시", 도쿄 "일본 도쿄 지요다구", 파리 "파리, 프랑스". `MKMapItem.name` 은 POI·거리 주소·우편번호가 와서 쓰지 않는다). 쓸 필드가 없으면 이름 없음이다. 시간대는 첫 항목의 `MKMapItem.timeZone` 이다(실측: 바다는 "GMT-1000" 같은 고정 오프셋). 항목이 없으면(`MKError.placemarkNotFound`, 실측상 북극 같은 곳) nil, 요청을 만들지 못하거나 그 밖의 오류면 실패(`PlaceNameError.failed`)다. 요청은 Task 취소를 받지 않아 끝까지 가고, 진행 중 `cancel()` 을 부르면 응답이 영영 오지 않아(실측) 부르지 않는다. 좌표·장소 이름은 로그에 남기지 않는다) ③ Interface 의 좌표는 자체 `Sendable` 값 타입으로 둔다(`CLLocationCoordinate2D` 노출 금지). Shared·Interface·Testing 의 CoreLocation·MapKit import 는 lint(`location_map_only_outside_shared_interface`)가 막고, Feature 의 `Map` 렌더링 외 사용은 리뷰로 잡는다. 이때 **위치 좌표만** Apple 로 가고 사진과 OCR 텍스트는 보내지 않는다. | 여행 판정 | 이미지 라벨이 아니라 위치·날짜로 판단한다(Core `TravelDetector` 순수 함수, 결과는 Core `Trip` = 사진 식별자·기간·중심점. 중심점은 사진이 가장 많은 칸 안의 사진 평균이라 자주 가는 지역이나 여행지 사이에 떨어지지 않는다). 여행은 "평소와 다른 곳"이라서 먼저 자주 가는 지역을 정한다: 지역 칸(위도·경도 0.18도. 위도 방향 약 20km, 서울에서 경도 방향 약 16km)마다 방문(그 칸과 맞닿은 칸에서 빈 날 하루까지 이어 사진을 찍은 기간 중 그 칸에 들른 날들. 맞닿은 칸을 오가도 한 번)을 묶고, 사진이 속한 방문의 앞뒤 3개월 안에 방문이 3번 이상이거나 첫날과 마지막 날이 60일 이상 떨어진 방문이 있는 곳, 보관함 전체에서 찍은 날이 가장 많은 곳(보관함이 짧거나 집 사진이 드물 때를 위해), 그리고 그 칸에 맞닿은 칸. 사진 수나 날 수로 세면 여행에서 많이 찍거나 오래 머문 곳이, 달로 세면 달 경계에 걸친 여행 하나가 두 번으로 세어지므로 방문으로 센다. 보관함 전체가 아니라 그 방문 무렵을 보므로 몇 년 또는 몇 달에 걸쳐 같은 곳에 간 여행도 각각 여행이고(3개월 간격 이하로 세 번 이상 가면 가운데 방문은 자주 가는 곳으로 본다), 달 경계에 걸친 체류도 60일 미만이면 여행이다. 60일 이상 머문 곳은 생활한 곳으로 본다. 방문 단위로 판정하므로 여행이 중간에 잘리지 않는다. 이사한 곳·본가처럼 자주 가는 곳이 여럿이어도 규칙 하나로 처리한다. 자주 가는 지역 밖에서 찍은 사진을 빈 날 하루까지 이어 묶고, 중간에 자주 가는 지역에서 찍은 사진이 있으면(같은 날이어도) 끊는다. 5장 미만인 묶음은 버린다(당일치기는 포함). 위치나 날짜가 없는 이미지는 쓰지 않는다. 자주 가는 지역은 판정 안에서만 쓰고 저장하거나 보여 주지 않는다. 수치는 임시이며 정확도 측정 작업에서 조정한다. 제한 접근(`.limited`)이면 사용자가 고른 사진만으로 판정하고, 정확도가 낮을 수 있다고 화면에 안내한다 |
| 여행 폴더 | 보관함의 여행 줄을 누르면 여행 폴더 목록(LibraryFeature `TripListView`·`TripListModel`)을, 그 줄을 누르면 여행 폴더 상세(`TripDetailView`·`TripDetailModel`)를, 상세의 칸을 누르면 사진 상세(카테고리 화면 행)를 연다. 목록: 저장소 `trips()` 의 여행을 최신 여행(시작 시각 내림차순, 같으면 끝 시각 내림차순)부터 보이고, 줄마다 기간·사진 수·대표 썸네일(가운데 → 첫 → 마지막 사진 중 저장소에 있는 첫 장. 모든 여행의 후보를 `assets(ids:)` 한 번으로 읽는다)·지금 로캘로 캐시된 장소 이름(없거나 이름 없음이면 기간을 제목으로)을 보인다. 사진 식별자가 없는 여행은 뺀다. 목록은 지오코딩하지 않는다(목록 Model 은 Map Client 를 받지 않는다). 장소 캐시는 읽기마다 `places(for:localeIdentifier:)` 한 번으로 읽고, 캐시된 시간대가 있으면 기간을 그 시간대로 계산한다. 제한 접근이면 고른 사진만으로 여행을 찾았다고 안내한다(여행 판정 행). 상세: 장소 이름(없으면 기간), 기간·사진 수, 반올림 중심점 핀 하나의 고정 지도(위치·지도 행), 여행 사진 격자(촬영순, 저장소에 없는 사진은 빼고 그 수를 안내), 그 기간(`TripPeriod.captureInterval`)의 영수증 → 지도 → 문서·메모 캡처 묶음(`assets(in:createdIn:)` 의 최신순을 촬영순으로 뒤집는다, 빈 묶음은 뺀다). 썸네일은 목록·상세 모두 `CategoryModel.thumbnailScreenAppeared(category: .travel)` 로 카테고리 화면과 같은 보관 규칙(64장)을 쓴다. 같은 여행 찾기: 여행 판정은 저장소가 바뀔 때마다 다시 돌아 같은 여행도 값이 바뀌므로, 상세는 다시 읽을 때마다 보던 여행과 사진이 가장 많이 겹치는 저장된 여행(Core `Trip.bestMatch(in:)`. 겹침이 같으면 시작 시각 차가 작은 것, 그다음 이른 것)을 같은 여행으로 본다. 겹치는 여행이 없으면 "여행을 찾을 수 없습니다"를 보이고 이름을 묻지 않으며, 보던 여행을 둬서 여행이 돌아오면 다시 찾는다. 다시 읽기는 카테고리 화면 행과 같다(`storeRevision`·날짜 변경 신호, 한 번에 하나씩·합치기, 닫은 뒤·다시 연 뒤 늦은 결과 버림, 처음 실패만 다시 시도, 다시 읽기 실패는 지난 내용을 둔다. 상세는 여행·장소 캐시·사진·기간 캡처 읽기 중 하나라도 실패하면 실패다). 상세는 사진 상세에서 돌아오면 지난 내용을 두고 마지막으로 찾은 여행을 계속 기준으로 삼는다. 목록에서 새로 열면 누른 여행을 기준으로 다시 찾고, 누른 여행이 보이던 여행과 같은 값일 때만 지난 내용을 두며 그 밖에는(판정이 여행을 나눈 뒤 다른 쪽을 연 경우 포함) 불러오는 중부터 보인다. 화면은 자기 방문(visit)의 내용만 그려 다른 여행을 연 첫 프레임에 지난 여행이 비치지 않는다. 기간(Core `TripPeriod`): 표시 날짜는 여행지 시각으로 첫 사진 날 ~ 마지막 사진 날이고, 캡처 범위는 첫날 0시 ~ 마지막 날 다음 날 0시 전이다. PhotoKit 은 사진의 시간대를 주지 않으므로(`PHAsset` 에 시간대 속성 없음), 상세에서 받은 여행지 시간대(`MKMapItem.timeZone`)가 캐시돼 있으면(시간대를 아는 여행) 그 시간대로 그대로 계산한다. 캐시가 없으면(목록만 봄, 오프라인 첫 열기, 요청 실패·시한, 항목 없음) 대체 규칙: 경도/15 로 추정한 오프셋이 기기 오프셋과 1시간 이하로 다르면 기기 시간대·여유 E=2시간(서울 기기에서 시드니 일광절약·마가단은 실제 차가 2시간이라 줄이면 누락), 아니면 추정 고정 오프셋·E=3시간으로, 범위를 `dayStart(첫 사진 − E) − E ~ dayEnd(마지막 사진 + E) + E` 로 넓힌다. 실제 오프셋이 그 시간대 ± E 안이면 여행지 기간의 캡처가 빠지지 않는다(설계 실험: 77곳 × 52주, 첫·마지막 시각 20분 간격에서 누락 0). 대신 앞뒤 E 의 다른 날 캡처가 섞이고, 첫(마지막) 사진이 자정에서 E 안이면 그쪽 하루 전체 + E 가 섞인다. 알려진 한계 (a): 시간대를 모르는 여행은 국내·일본처럼 기기 시간대가 실제와 같은 곳과 경도 추정이 맞는 곳을 뺀 해외 대부분에서, 첫·마지막 사진이 여행지 자정에서 그 차이(0.25~3시간, 일광절약 중이면 더) 안이면 첫날·마지막 날 표시가 하루 밀린다(날짜변경선 나라는 기간 전체가 하루 이르다). 목록에서는 상세를 연 적 없는 해외 여행에 생기고, 상세를 온라인으로 한 번 열면 시간대가 캐시돼 목록·상세 모두 고쳐진다. (b): 시간대를 알아도 중심점(사진이 가장 많은 칸)의 시간대 하나로 계산하므로, 여러 시간대 여행에서 중심과 다른 시간대의 첫(마지막) 사진이 여행지 자정에서 두 시간대 차이 안이면 그날이 하루 밀려 표시가 바뀌고 그날 캡처가 빠진다(반대쪽이면 섞인다. 예: 런던 → 파리 여행의 첫 사진이 런던 23:30). 두 한계는 `TripPeriodTests` 에 기대값과 이유로 남긴다. 장소 이름: 상세를 열 때만, 다시 읽기에서 장소 캐시에 지금 로캘 이름이 없을 때만 여행 중심점의 반올림 키(`Trip.placeKey`)와 그 로캘로 `MapClient.placeName(near:locale:)` 를 부른다(위치·지도 행). 받은 이름·시간대는 캐시에 쓰고(`savePlace`, 저장소 행), 시간대를 받으면 다시 읽어 기간·캡처를 그 시간대로 다시 계산한다. 그래서 첫 온라인 열기에서 응답(실측 0.1~0.4초) 뒤 캡처 묶음이 한 번 바뀔 수 있다: 대체 범위가 실제 범위를 포함하므로 섞였던 캡처가 빠질 뿐 빠지던 캡처가 생기지는 않는다. 묻는 동안 "장소 확인 중"을 보이고, 쓸 이름 필드가 없거나 항목이 없으면(항목 없음은 캐시하지 않는다) 기간을 제목으로, 요청이 실패하거나 15초(임시, 오프라인 동작을 실기기에서 확인하지 못함) 안에 응답이 없으면 기간을 제목으로 보인다. 시한이 지나도 요청은 계속 가고 끝나면 캐시에 쓰며, 그때 상세가 열려 있으면 다시 읽어 이름·시간대를 반영한다. 다시 묻는 규칙(visit 은 상세 화면 인스턴스마다 만드는 View `@State` 값, §1 규칙 8): 한 방문 안에서는 키마다 받은 결과(이름·이름 없음·못 찾음)를 기억해, 사진 상세에서 돌아오거나 판정이 키를 바꿨다 되돌려도(되돌린 키의 캐시는 `replaceTrips` 가 지웠을 수 있다) 그 결과를 다시 쓰고 다시 묻지 않는다. 되돌린 키의 캐시(시간대 포함)가 지워졌으면 그 방문 동안 기간·캡처는 대체 규칙이고, 시간대는 다음 방문에서 다시 물어 얻는다. 목록에서 새로 열면 기억을 비워 캐시가 없는 키를 한 번 다시 묻는다. 아직 "장소 확인 중"이던 키는 진행 중 요청을 이어받고, 그사이 실패·시한으로 비었으면 다시 묻는다. 이름은 늘 지금 보이는 여행의 키 것이고, 키가 바뀌면 지난 키의 응답을 기다리지 않는다(요청은 끝까지 가서 캐시에 쓴다). 같은 키·로캘의 진행 중 요청이 시작한 지 시한 안이면 새 방문도 이어받아 두 번 묻지 않는다. 화면을 닫은 뒤 끝난 응답은 상태에 쓰지 않고 캐시에만 쓴다. 응답이 오지 않는 요청은 취소할 수 없어(위치·지도 행) 시한이 지난 뒤 새 방문마다 하나씩 더 나가 남는다(드문 경우로 받아들인다). 판정이 바뀌어도 중심점 키가 같으면 다시 묻지 않고, 키가 바뀌면 새 키로 한 번 묻는다 |

분석하고(동시 처리 수는 1만 장 측정 작업에서 정한다) 1단계는 50장(임시)마다 저장·삭제하고 2단계는 10장(임시, 실기기에서 조정)마다 저장한다. 저장소의 식별자 목록 조건 크기를 이 수로 묶고, 중간에 멈춰도 이 수만큼만 다시 분석한다. 다시 시작하면 1단계를 마친 이미지는 다시 분류하지 않고 저장소의 대기 목록으로 2단계를 이어 한다. 저장된 기프티콘 중 지금 규칙 버전으로 추출하지 않은 이미지(저장소 경량 이전 뒤, 규칙 버전을 올린 뒤)는 전체 비교 때 저장소의 추출 대기 목록으로 골라, OCR 없이 저장된 줄로 소급 추출한다. 지금 규칙 버전으로 추출하지 않은 영수증도 같다(`receiptExtractionPendingIDs`. 대상은 기프티콘과 따로 둔다). 루프는 변경 → 소급 추출(기프티콘 → 영수증) → 2단계 → 소급 보강(아래) 순으로 하고(소급 추출은 순수 계산과 저장소 왕복뿐이라 OCR 보다 훨씬 짧다. 소급 보강은 모델 호출이라 OCR 처럼 느려 카테고리·개수를 바꾸는 2단계 뒤에 둔다) 배치 경계마다 변경을 먼저 반영한다. 소급은 1단계와 같은 50장씩 읽어 추출 값만 저장하고(고른 배치는 저장할 것이 없어도 대상에서 빼 같은 실행에서 다시 돌지 않는다), 소급 대상을 조회하거나 배치를 읽고 저장하지 못하면 이번 실행에서는 그 소급만 멈추고(대상을 비운다. 기프티콘·영수증 소급은 서로를 멈추지 않는다) 분류·글자 읽기는 이어 가며, 다음 실행이나 전체 다시 비교 때 다시 시도한다(소급은 카테고리·개수를 바꾸지 않아, 이것으로 멈추면 다 분석한 뒤 '새 사진을 분류하지 못했다'는 틀린 안내가 나온다). 소급은 카테고리·개수를 바꾸지 않고 저장소 이전·규칙 버전 변경 때 한 번만 생기므로 진행률과 `isFinished` 에 넣지 않는다. 그래서 `isFinished` 뒤에도 소급이 남아 있을 수 있어 추출이 끝났다는 뜻으로 쓰지 않는다. 대신 소급 대상이 비면(다 마쳤거나 실패로 멈춤. 기프티콘·영수증 따로 각자 한 번) 같은 값의 진행률을 한 번 보내, 받는 쪽이 추출 값으로 다시 계산하게 한다(만료 알림 행. 열린 영수증 목록도 다시 읽는다, 카테고리 화면 행). 저장된 기프티콘 중 언어 모델 보강을 마치지 않은 이미지(경량 이전 뒤, 모델을 쓸 수 없을 때 저장, 보강 버전을 올린 뒤의 다른 보강 버전, 출처 속성이 생기기 전에 마친 옛 행. 저장소 행)는 전체 비교 때 **모델을 쓸 수 있는지와 관계없이** 저장소의 보강 대기 목록으로 고르고, 소급 추출로 다시 추출한 값에 채울 필드가 있으면 같은 실행의 대상에 더한다(빈 필드가 있지만 규칙 단서로 막혀 채울 것이 없는 행은 보강 대기로 남아 다음 실행이나 전체 다시 비교의 소급 보강이 모델 없이 마친다. 알림에는 영향이 없다). 소급 보강은 2단계와 같은 10장씩 저장된 줄로 규칙 추출부터 다시 계산하고, 채울 필드가 없으면 모델 없이 마치고, 있고 모델을 쓸 수 있으면 모델로 보강하며(입력 때문인 실패면 실패 수를 센다), 모델을 쓸 수 없으면(배치 도중 쓸 수 없게 되면 그 배치의 나머지도) 다른 보강 버전 행만 규칙 값으로 되돌리고 보강 대기 행은 건너뛴다(시스템 거부도 그 행은 같게. 배치 나머지는 계속 묻는다)(저장소 행의 보강 결과). 출처 속성 전에 마친 옛 행(`.sourcesUnknown`)은 규칙 추출을 다시 계산한 뒤 모델을 부르지 않고 저장된 값과 비교해 출처만 정해 마치므로(저장소 행), 모델을 쓸 수 있는지·연속 실패 차단과 관계없이 같은 결과다. OCR 줄이 없는 행은 채울 필드가 없는 것으로 보아 모델에 묻지 않고 마친다. 그래서 모델이 없는 기기에서도 옛 보강 버전의 모델 값이 같은 실행에서 규칙 값으로 바뀐다. 고른 배치는 결과가 없어도 대상에서 빼 같은 실행에서 다시 시도하지 않고, 건너뛴 행은 다음 실행이나 전체 다시 비교 때 다시 본다(모델을 쓸 수 없는 동안은 실행마다 조회·배치 읽기만 하고 쓰지 않는다). 대상을 조회하거나 배치를 읽고 저장하지 못하면 소급 추출처럼 이번 실행에서는 소급 보강만 멈추고, 모델 응답 도중 취소되면 그 배치를 저장하지 않는다. 소급 보강도 진행률과 `isFinished` 에 넣지 않고 대상이 비면(다 마쳤거나 실패로 멈춤) 같은 값의 진행률을 한 번 보낸다(소급 추출과 따로 각자 한 번). 모델이 한 실행에서 연속 3번(임시. 쓸 수 없음은 세지 않고 시스템 거부는 세며, 응답을 받으면 0 으로 돌아간다) 실패하면(시뮬레이터처럼 쓸 수 있다는데 요청이 모두 실패할 때) 다음 전체 다시 비교(`.reloadAll`)나 다음 실행까지 2단계와 소급 보강 모두 모델을 부르지 않는다(차단 중에도 소급 보강은 모델 없이 할 수 있는 것을 하고 대상이 비면 진행률을 보낸다). 실행 도중 모델을 쓸 수 있게 되면 2단계는 다음 이미지부터 모델을 쓰고, 그 전에 건너뛴 보강 대기는 다음 실행이나 전체 다시 비교 때 소급한다. 한계: 분류 보강은 2단계에서 한 번만 한다. 모델을 쓸 수 없었거나 실패했거나 연속 실패 차단으로 건너뛴 이미지는 기타로 저장된 채 다시 시도하지 않는다(보강 상태를 남기는 것은 기프티콘 추출뿐이고, 분류 보강 재시도는 저장된 이미지의 소급 재분류와 함께 별도 작업). 1단계에서 이미지를 읽지 못하거나(iCloud 에만 있음 `notAvailableLocally`·손상) 분석에 실패하면 저장하지 않고 미룬 수로 세어 다음 실행이나 `.reloadAll` 때 다시 시도한다. 2단계에서 원본을 읽지 못하거나 OCR 에 실패하면 1단계 결과(대기)로 남기고 2단계 미룬 수로 세어 같은 실행에서는 다시 하지 않고 다음 실행이나 `.reloadAll` 때 다시 시도한다(대기 상태로 구분되므로 사진형 카테고리를 잃지 않는다). 보관함에 없는 이미지(`notFound`)는 전체 수에서 빼고 여행을 다시 판정한다. 2단계에서 `notFound` 면 저장 결과는 지우지 않고(삭제는 보관함 변경이 한다) 대기에서만 빼고, 삭제 없이 다시 추가되면 대기로 되돌린다. 저장 수는 보관함에 있는 이미지만 센다. 1단계 도중에는 보관함 변경을 반영하지 않고, 2단계 도중 온 변경은 받아 두었다가 배치 경계에서 먼저 반영한다(새 이미지 1단계 뒤 2단계로 돌아온다. 새 사진이 OCR 대상이면 최신이라 다음 배치 맨 앞이다). 저장소를 읽거나 쓰지 못하면 멈추고 스트림을 끝낸다(소급 추출·보강은 위 예외). 사진을 읽을 권한이 없으면 조회 결과가 비어 저장 결과가 모두 지워지므로, 비교하지 않고 저장 결과를 그대로 둔 채 끝낸다. 여행 판정은 메타데이터만 보므로 분석을 기다리지 않고 보관함이 바뀔 때마다 전체를 다시 판정해 바꾼다. 이미 반영한 변경이 다시 와서 보관함이 그대로면 다시 판정·저장하지 않는다(판정 비용은 1만 장 측정 작업에서 확인한다). 한계: 보관함 변경 알림은 추가·삭제만 보내므로, 사진의 위치·날짜를 고치거나 iCloud 에만 있어 미룬 이미지가 기기로 내려와도 다음 `.reloadAll` 이나 다음 실행 전까지 반영하지 않는다. 내용 변경을 반영할지(`ImageChange` 에 변경 추가)는 별도 작업에서 정한다. 보관함 화면이 떠 있는 동안(`LibraryModel.onAppear()` 가 구독하는 동안, 진행률은 Model 상태 `indexingProgress`) 메인 밖 낮은 우선순위(`.utility`) Task 로 돌린다. 화면은 분석 중일 때만 진행률을 보여 주고 두 단계를 다 마치면(`isFinished`) 숨긴다. 1단계는 "이미지 분류 중" 막대(저장+미룸/전체), 2단계는 "글자 읽는 중" 막대(이번 실행에서 읽은+미룬 수 / 그 수+대기)와 "사진 분류는 끝났고 캡처는 글자를 읽으며 채운다"는 안내, 캡처 섹션의 "개수가 늘어날 수 있다" 안내를 보인다. `isFinished` 는 미룬 수(1·2단계)까지 더해 판단하므로, 미룬 이미지가 있으면 다 분석한 뒤에도 두 수를 합쳐 다음에 다시 시도한다고 안내한다. 첫 진행률은 보관함과 저장소 비교를 마친 뒤에 오므로, 그 전에도 분석 중(`isIndexing`)으로 안내한다. 정상이면 스트림이 끝나지 않으므로, 끝나면 첫 진행률을 받기 전이라도 멈춘 것(`isIndexingStopped`)으로 보고 다시 시도 버튼을 보여 준다(진행률을 받았으면 마지막 값도 함께. 2단계에서 멈췄으면 글자 읽기를 마치지 못했다고 남은 대기 수로, 다 분석한 뒤 보관함 변경을 반영하다 멈췄으면 개수 대신 새 사진을 분류하지 못했다고 안내한다)(다시 시도는 `run()` 을 다시 불러 저장된 데까지 건너뛴다. 원인별 안내는 `run()` 이 원인을 알려야 해서 별도 작업). 보관함 화면은 같은 저장소(PhotoStore Interface)를 직접 읽어 카테고리별 개수와 여행 수를 보여 주고, 저장(1·2단계)·삭제·여행 교체, 소급(추출·보강)이 끝날 때 오는 진행률을 받을 때마다, 그리고 멈출 때 다시 읽고(카테고리 화면·기프티콘 목록·영수증 목록·사진 상세·여행 폴더 목록·상세가 열려 있으면 그 화면도 다시 읽는다, 카테고리 화면 행) 만료 알림을 다시 맞춘다(만료 알림 행). 저장소를 열지 못하면 App 이 인덱서와 저장소 없이(nil) 주입하고 보관함만 보여 준다. 앱이 닫혀 있을 때의 처리(`BGProcessingTask`)는 별도 작업에서 정한다 |
