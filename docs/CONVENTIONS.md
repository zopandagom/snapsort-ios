# 개발 규칙: 해야 할 것 / 하지 말아야 할 것

사람과 Claude 모두에게 적용된다. 표의 "강제" 열은 어디서 자동으로 막히는지다. 빈칸이면 리뷰에서 잡는다.

## 1. 아키텍처
| ✅ 해야 할 것 | ❌ 하지 말아야 할 것 | 강제 |
|---|---|---|
| Model 상태는 `public private(set) var` | View 나 다른 타입이 Model 상태를 직접 대입 | 컴파일러 |
| View 는 이벤트 메서드(`onAppear()`, `xxxTapped()`, `xxxChanged(_:)`)만 호출 | `$model.x` 양방향 바인딩 | `no_two_way_model_binding` |
| 외부 시스템은 Client 로 감싸고 Interface / Impl / Testing 으로 나눈다 | Feature 에서 `import Photos`, `import Vision`, `import SwiftData` 등 | `system_framework_only_in_impl` |
| Impl 은 App 에서만 만들어 주입 | Feature·Interface·Testing 이나 다른 Client 의 Impl 에서 `import …Impl` (Impl 이 다른 Client 를 조합할 때는 그 Interface 만) | `impl_import_only_in_app` |
| Fake 는 Testing 모듈에 두고 Tests·Example 에서만 사용 | 프로덕션 코드에서 `import …Testing` | `testing_import_not_in_production` |
| `#Preview` 는 Feature 의 Example 타깃에 | Feature Sources 에 Fake 를 만들어 Preview 작성 | |
| Feature 끼리 필요한 공유는 Client 나 Shared(Core) 로 | Feature 가 다른 Feature 에 의존 | 템플릿 |
| Shared 는 Client 와 Apple 데이터 프레임워크 없이 | Shared 에서 Client 모듈이나 Apple 데이터 프레임워크 import | `shared_independent_of_clients`, `system_framework_only_in_impl` |
| 좌표는 Core `Coordinate` 로 넘긴다 | Shared·Interface·Testing 에서 `import CoreLocation`, `import MapKit` | `location_map_only_outside_shared_interface` |
| 화면 코드는 Feature·DesignSystem 에 둔다 | Core 에서 `import SwiftUI`, `import UIKit` | `core_no_ui_framework` |
| Apple 데이터 프레임워크와 CoreLocation·MapKit 밖의 부수효과 없는 iOS 프레임워크(CoreGraphics·ImageIO 등)는 Core 를 포함한 모든 레이어에서 쓴다 | 의존 규칙을 지키려고 변환·재인코딩 같은 실행 비용을 들이기 | |
| 새 모듈은 `Module.swift` 의 enum 과 `Project.client/feature/shared` 템플릿으로 | 매니페스트에서 `Target` 을 직접 만들거나 빌드 설정을 덮어쓰기 | |

## 2. Swift / 동시성
| ✅ | ❌ |
|---|---|
| Model 은 `@MainActor @Observable final class` | `ObservableObject` / `@Published` (구 방식) |
| Client 프로토콜은 `Sendable`, 입출력도 `Sendable` 값 타입 | `@unchecked Sendable`, `nonisolated(unsafe)` 로 경고 숨기기 (불가피하면 이유를 주석으로) |
| 무거운 동기 작업(PhotoKit 조회, OCR)은 Impl 에서 `@concurrent` 로 메인 밖에서 | Model 에서 `Task.detached` 로 우회 |
| 에러는 Interface 에 도메인 에러 타입으로 정의해 던진다 | Feature 에 `PHPhotosError`, `VisionError` 같은 프레임워크 에러가 새어 나오기 |
| 강제 언래핑 대신 `guard let` / 기본값 | `!`, `try!` (테스트 제외) |
| 명시적 `self.` (SwiftFormat 이 자동 삽입) | |

## 3. 테스트
| ✅ | ❌ |
|---|---|
| Swift Testing(`import Testing`, `@Test("한국어 설명")`, `#expect`) | 새 테스트를 XCTest 로 작성 |
| Model 의 모든 public 이벤트 메서드에 테스트: Fake 주입 → 이벤트 호출 → 상태 검증 | View 를 스냅샷/UI 테스트로만 검증 |
| Client Impl 은 순수 로직(매핑, 파싱)을 분리해 `@testable` 로 테스트. 여러 Client 결과를 받아 판단하는 규칙(규칙 분류, OCR 대상 판정, 여행 판정)은 Core 순수 함수로 두고 테스트 | 실제 사진 보관함·권한 팝업에 의존하는 테스트 |
| OCR 대상 판정·규칙 분류 정확도는 Core `Tests/Fixtures/ClassificationSamples.json` 의 샘플로 회귀 테스트. 샘플은 이미지가 아니라 분류 입력(스크린샷·위치 여부·크기, Vision 라벨, OCR 줄)과 기대 카테고리다(Vision 분류는 시뮬레이터에서 돌지 않아 실기기에서 기록한다). 샘플은 Debug 기록 도구로 기록한다: 초안의 `predicted` 를 보고(보관함 전체 정확도 초안은 기록 화면의 '샘플 보기'에 번호 목록을 넣어 사진을 보고) `expected` 를 채우고 `predicted` 를 지운 뒤 이름을 설명형으로 바꾼다. 보관함 전체 정확도 모드로 기록한 초안은 OCR 대상이 아닌 샘플에 `ocrSkipped` 가 있다(그대로 픽스처에 둔다). 라벨은 0.01 이상까지 담고 테스트가 Core 기준으로 거른다. 원본이 기기에 있는 상태에서 기록한다(iCloud 대체 버전으로 읽은 샘플은 OCR 이 실제와 다를 수 있다). (시드 샘플: `ClassificationAccuracyTests` 머리 주석) 실제 사진에서 기록한 OCR 줄은 이름·전화번호·주소·대화 내용·쿠폰·바코드 번호를 가린 뒤 커밋한다 | 이미지 파일, 위치 좌표, 가리지 않은 OCR 텍스트를 픽스처로 커밋 (레포가 공개다) |
| Foundation Models 테스트는 `.enabled(if: SystemLanguageModel.default.isAvailable)` 로 조건부 | CI 에서 모델 없다고 실패하는 테스트 |
| 실패하는 테스트는 고친다 | 테스트 삭제·`.disabled` 로 통과시키기 (필요하면 먼저 합의) |
| 사용자와 합의해 미룬 알려진 오분류·누락은 원하는 동작을 `withKnownIssue("이유")` 로 감싸 남긴다(정확도 샘플은 `knownIssue` 필드에 이유를 적으면 테스트가 감싼다). 지울 시점(예: 정확도 측정 작업)을 주석에 적고(정확도 샘플은 JSON 이라 `knownIssue` 이유 문자열 끝에 ` — <지울 시점>에서 지운다` 로 적는다), PR 본문 "검증 · 리뷰"에 `합의(withKnownIssue): 이유, 지울 시점` 으로 적는다 (리뷰 지적의 처리가 아니다, §5 "리뷰 지적 처리"). 정확도 샘플의 `knownIssue` 도 `withKnownIssue` 하나로 본다(샘플 하나 = 항목 하나. 합의 줄은 `합의(withKnownIssue): <샘플 이름>: 이유, 지울 시점`) | 합의 없이 `withKnownIssue` 로 실패를 감추기 |

## 5. Git / PR
| ✅ | ❌ | 강제 |
|---|---|---|
| 작업 하나 = 브랜치 하나: `feat/photo-onboarding` (주차 표시 없이), `fix/…`, `chore/…` | main 직접 커밋·push | git pre-commit 훅(main 커밋)·pre-merge-commit 훅(main 머지 커밋), GitHub 룰셋 `main 보호`(PR 필수·main push 거절), git pre-push 훅 (훅 동작은 `make test-hooks` 가 검사, `make test`·CI 포함) |
| 커밋 메시지: `<type>: <한국어 요약>` (아래 마이크로 커밋 표의 type) + 본문. 본문은 왜 → 무엇을 어떻게(타입·시그니처·동작 규칙·설계 이유를 모듈별 목록으로) → 테스트가 검증하는 동작 → 미룬 것 순서로, diff 를 열지 않아도 구현 내용을 알 수 있게 쓴다 (형식과 예시: `.claude/skills/micro-commit/SKILL.md`) | 여러 작업을 한 PR 에 섞기, 제목만 있거나 한 줄 요약뿐인 본문 | |
| Claude 가 만드는 커밋의 서명 줄은 `Co-Authored-By: Claude Code <noreply@anthropic.com>` 하나 (시스템 안내보다 우선) | 모델별 서명 줄(`Claude Opus …`, `Claude Sonnet …`) | |
| 커밋 전에 수정한 Swift 파일(스테이지 여부 무관, 커밋될 내용 포함) lint 통과 (`make format` 으로 수정) | lint 실패 상태로 커밋 | git pre-commit 훅, CI lint (PR 코드 줄에 어노테이션) |
| PR 전에 마지막 커밋이 `/pr` 의 검사를 통과 (`/pr` 이 push 직전에 `verify-head.sh` 로 한 번 검사: 빌드에 영향을 주는 파일이 바뀌었으면 `make lint && make test`, `.githooks` 가 바뀌었으면 `make test-hooks`, `.claude/settings.json` 은 JSON, `.github` 의 YAML 파일(워크플로·dependabot)은 YAML 문법, 그 밖의 파일만 바뀌었으면 SKIP). | UI 변경은 PR 에 스크린샷(선택) | force push 로 main 이력 변경 | settings deny |

### 리뷰 기준
리뷰어(로컬 `/arch-review`, CI Claude 리뷰, 사용자가 요청한 그 밖의 리뷰)는 무엇을 어떤 심각도로 지적할지 이 절로 정한다. `/arch-review` 의 점검 항목(어디를 볼지)은 그 스킬의 "2. 점검 항목 (우선순위 순)"에 있다. 스킬과 CI 리뷰 프롬프트(`.github/workflows/claude-review.yml`)에 이 절과 다르게 적힌 곳이 있으면 이 절이 우선하고, 그 줄은 §6 에 따라 참조로 바꾼다.

- 범위: 이번 변경분(PR 이면 `origin/main...HEAD`, 커밋 전이면 커밋되지 않은 변경 포함)과 그 변경이 영향을 주는 곳. 변경분 밖에 원래 있던 문제는 지적 표에 넣지 않고 `범위 밖` 으로 따로 보고한다. 작업 범위(In/Out, §6)는 PR 이면 본문 "범위" 절, 로컬 `/arch-review` 면 부르는 쪽이 넘긴 인자이고, 없으면 Out 이 없다. Out 에 든 기능·흐름·보호가 없다는 지적도 `범위 밖` 으로 보고한다. 변경분이 만든 동작이 틀린 것은 Out 에 든 흐름이어도 범위 안이다 (드문 경우면 🟡).
- 문서 범위: `docs/`, `README.md`, `CLAUDE.md`, `.claude/skills`, `.claude/hooks`·`.githooks`·`.github/scripts` 의 주석, `.github` 의 PR 템플릿과 워크플로(프롬프트·주석), `.swiftlint.yml` custom_rules 의 `message`, `Makefile` 주석, 코드의 문서 주석.
- 이번 변경과 관련된 문서 줄: 바뀐 줄, 그리고 바뀐 동작·규칙을 설명하는 줄. 바뀐 식별자와 바뀐 규칙의 핵심 문구로 문서 범위를 검색해 찾는다.
- 문서 불일치: 같은 동작이나 규칙을 서로 다르게 설명하는 것. 사실(값·이름·동작·명령·절차)이 다르면 사실 불일치, 같은 사실을 다른 말로 쓴 것은 표현 차이다. 규칙을 다시 적지 않고 절을 가리키기만 하는 줄은 불일치가 아니다.
- 드문 경우: 발생 조건이 정상 흐름에서 생기지 않는 것. 정상 흐름은 앱이면 사용자가 보통 하는 조작과 사용자 조작이나 기기·계정 상태만으로 생기는 실패(권한 거부·제한 접근, 빈 결과, 저장 공간 부족, iCloud 에만 있는 원본), 문서·하네스면 문서·스킬이 정한 절차와 장치가 막으려는 실수(위협 모델)다. 드문 타이밍, 그 실수가 장치를 거치지 않는 드문 경로(예: main 에서 `git cherry-pick`·`git revert` 로 만든 커밋)로 오는 것, 의도적 우회, 가상의 입력, 정해진 설정(`make bootstrap` 등)을 건너뛴 환경이 드문 경우다.
- 🔴 필수: 버그, 동시성 오류, ARCHITECTURE·이 문서의 규칙 위반(§3 테스트 누락은 🟡), 개인정보 위반, 실패해도 통과하는 경로(fail-open. 그렇게 되는 재현(명령·절차)을 들 수 있을 때), 함께 지킬 수 없는 규칙(실제로 부딪히는 흐름을 들 수 있을 때), 이번 변경과 관련된 문서의 사실 불일치. 단 드문 경우에서만 생기는 지적은 데이터 손실·잘못된 저장, 개인정보(§4), 사용자가 회복할 수 없는 상태가 아니면 🟡 이다.
- 🟡 권장: 드문 경우에서만 생기는 🔴 항목, 문서의 표현 차이, §3 이 요구하는 테스트 누락, 테스트 보강, 이름, 그 밖의 개선. 등급은 보류 기준에 맞추려고 낮추지 않는다.
- 모든 지적의 "문제"에는 발생 조건(어떤 흐름·타이밍에서, 드문 경우인지)과 사용자 영향(보이거나 남는 것이 바뀌는지, 저절로 회복되는지)을 적는다.
- 지적하지 않는 것: lint·format 으로 잡히는 스타일, 취향 차이, 합의 여부만을 근거로 한 새 `withKnownIssue` (리뷰어는 대화 속 합의를 모른다. 확인은 `/pr` 이 한다. 이유·지울 시점(주석. 정확도 샘플은 이유 문자열 끝)이 없는 것처럼 다른 근거가 있으면 그 근거로 지적한다).
- 리뷰어는 처리(아래 "리뷰 지적 처리")를 정하지 않는다.

### 리뷰 지적 처리
리뷰 지적은 고치는 것이 기본이다. 처리는 아래 네 가지이고 사용자가 정한다 (`/pr` 이 추천한다). 처리에 쓰는 심각도는 위 "리뷰 기준"의 정의로 판단한다 (§3 이 요구하는 테스트 누락뿐인 지적은 🟡). 리뷰어 표시가 더 높으면 그 근거(어느 🔴 항목에 든다는 주장과 발생 조건)가 사실인지 파일:줄이나 실행 결과로 확인한다. 드문 경우인지는 발생 조건이 정상 흐름("리뷰 기준")에서 생기는지로 본다. 사실이면 그 높은 등급이고, 틀리면 반박 근거를 보이고 정의의 등급으로 처리한다. 등급의 근거가 틀린 것만으로는 기각하지 않는다 (기각은 지적의 전제가 틀릴 때다). 🔴 필수는 반영·기각·범위 밖으로만 처리한다.

| 처리 | 쓸 수 있는 지적 | 기록 형식 |
|---|---|---|
| 반영 | 모두. 사용자가 고치기로 정하면 정해진다. 고쳤는지는 다시 도는 리뷰가 본다 (아래 "같은 지적") | 본문에 적지 않는다. CI 지적의 GitHub 답은 `반영: 무엇을 어떻게` |
| 보류 | 🟡 중 아래 기준 하나에 맞고 "보류할 수 없다"에 들지 않는 지적 | `보류(기준 k: 이유)`. 기준 3 이면 `보류(기준 3: 이유, 후속: 무엇)` |
| 기각 | 전제가 사실과 다른 지적 (🔴 포함). 파일:줄이나 실행 결과로 그 전제를 반박할 수 있을 때만. 합의 여부만을 근거로 한 `withKnownIssue` 지적은 사용자가 합의를 확인하면 기각이다 (근거: 본문 합의 줄) | `기각(근거: 파일:줄, 실행 결과 또는 본문 합의 줄)` |
| 범위 밖 | 변경분 밖에 원래 있던 문제, Out 에 든 기능·흐름·보호가 없다는 지적 ("리뷰 기준"의 범위) | `범위 밖(후속: 무엇)`. 🔴 에 해당하면 후속은 별도 `fix/…` 브랜치다 (Out 이어도 같다). Out 에 든 🟡 는 후속이 없으면 `범위 밖(Out)` |

본문 처리 줄은 고치지 않고 남긴 지적(보류·기각·범위 밖)만 리뷰어가 어느 지적의 처리인지 읽을 수 있게 `<지적 요약>: <기록 형식>` 으로 쓴다. GitHub 답은 지적마다 기록 형식으로 시작한다 (요약-only 지적은 그 지적을 인용한 줄 다음 줄부터). 리뷰어 표시보다 낮은 등급으로 처리한 지적은 기록 뒤에 `(등급 🟡: 표시 근거를 반박하는 파일:줄·실행 결과, 또는 드문 발생 조건)` 를 붙인다.

| 기준 | 보류할 수 있는 지적 | 예 |
|---|---|---|
| 기준 1 | 동작·사용자 영향 없음: 사용자가 보거나 남는 것이 바뀌지 않는다. 앱은 화면·저장 결과·알림, 문서·하네스는 에이전트가 하는 일(멈춤·진행·실행하는 명령)과 남기는 기록(커밋·PR 본문·GitHub 답)이다 (다음 진입·이벤트에서 덮이는 내부 상태 포함) | 화면이 사라진 뒤 남는 상태 값 |
| 기준 2 | 드문 경우에서만 생긴다 ("리뷰 기준"의 드문 경우. 드물어서 🟡 가 된 🔴 항목 포함) | 빠른 재진입 직후 지난 안내가 잠깐 보임, main 에서 `git cherry-pick`·`git revert` 로 만든 커밋이 pre-commit 을 거치지 않음 |
| 기준 3 | 고치는 비용이 PR 범위를 넘음: Interface 변경, Fake 확장 같은 별도 작업이 필요하다 | 도중 실패를 흉내 내는 Fake 가 필요한 테스트 |

보류할 수 없다 (권장이어도 보류하지 않는다. 반영이나 위 표에서 쓸 수 있는 다른 처리를 쓴다):
- 🔴 필수 전부 (처리는 위 첫 문단)
- 데이터 손실·잘못된 저장, 개인정보 (§4)
- 사용자가 회복할 수 없는 상태 (다시 시도가 계속 반응하지 않음, 앱을 다시 켜기 전까지 틀린 화면)
- 흔한 사용 흐름(첫 실행, iCloud 저장 공간 최적화 등)에서 보이는 문제

§3 표가 요구하는 테스트의 누락(예: Model 이벤트 메서드, Client Impl 순수 로직, Core 규칙 함수)은 기준 3 으로만 보류할 수 있다 (기준 1·2 불가).

같은 지적: 고칠 대상(파일과 절·함수)과 전제(지적이 사실이라고 본 것)가 같으면 같은 지적이다. 줄 번호·표현이 달라도 같다. 이 대화에서 이미 정한 지적이 다시 올라오면 그 결정을 따르고 다시 묻지 않는다. 고치기로 정했는데 정한 뒤에 돈 리뷰(그 뒤 `/pr` 의 `/arch-review`, 그 뒤 push 한 head 의 CI 리뷰)에 또 올라오거나, 결정 근거를 반박하는 새 사실(다른 파일:줄, 새 발생 조건)이 함께 왔거나, 사용자가 원하면 다시 정한다. 다른 대화(새 세션)에서 정한 결정은 쓰지 않고 다시 정한다.

지적과 대응은 같은 곳에 둔다 (리뷰어가 읽는 소통 기록이다. `/pr` 은 이 대화에서 처리를 정한 지적에 답한다):
- CI 가 아닌 리뷰(로컬 `/arch-review`, 사용자가 요청한 다른 리뷰)의 지적: PR 본문 "검증 · 리뷰"의 처리 줄 (반영은 적지 않는다, 위 "본문 처리 줄")
- CI 리뷰 인라인 지적: 그 스레드에 Reply
- CI 리뷰 요약 코멘트에만 있는 지적: 그 요약 코멘트를 인용·링크하는 PR 코멘트

기록(본문 처리 줄·합의 줄, GitHub 답)은 덧붙이기만 한다. 이미 있는 줄과 답은 지우거나 고치지 않고, 같은 대화에서 이미 올린 기록은 다시 올리지 않는다. 기록은 소통용이고 `/pr` 은 이것으로 결정을 판정하지 않는다.

후속(기준 3 보류, 범위 밖)은 머지를 막지 않는다. 기록 줄에 적고, 머지 뒤에도 남도록 Claude 프로젝트 메모리에 옮긴다 (GitHub 이슈는 쓰지 않는다). 후속 작업이 끝났다고 사용자가 확인하면 메모리에서 지운다 (자동으로 지우지 않는다).

머지 전 확인 (머지하는 사용자가 본다): 마지막으로 push 한 head 의 CI 리뷰 요약(`## Claude 리뷰`)이 올라왔고(CI 리뷰 갈음 PR 은 로컬 `/arch-review`), 그 지적을 포함한 모든 리뷰 지적의 처리를 정하고 표의 기록 형식대로 기록했다. 해당하는 수동 확인(§5 표 "수동 확인" 행)을 마쳤다. 요약에 새 지적이 있으면 `/pr` 을 다시 실행해 처리한다. CI 리뷰가 실패했거나 돌지 않았으면 다시 돌릴지 이대로 머지할지 사용자가 정한다. 필수 체크 `ci-result`(lint·test)는 GitHub 룰셋이 따로 막는다. dependabot PR 은 CI 리뷰가 돌지 않으므로 `ci-result` 와 사용자 확인으로 머지한다.

### 마이크로 커밋
작업은 **역할별로 구현 → 검증**하고, 커밋은 **사용자가 지시할 때** 역할별로 나눠서 한다. 한 번에 몰아서 커밋하지 않는다.

| type | 역할 | 예 | 검증 항목 |
|---|---|---|---|
| `build` | 도구 버전, Tuist 템플릿, Makefile | `.mise.toml`, `Tuist/`, `Workspace.swift`, `Makefile` | `make project` (+ `make test` 영향 시) |
| `feat` / `fix` / `refactor` | 코드 구현 (**해당 테스트 포함**) | `Projects/**` | `make lint && make test` |
| `test` | 기존 코드에 테스트만 추가 | `Projects/**/Tests` | `make test` |
| `style` | 포맷·lint 설정과 그에 따른 일괄 포맷 | `.swiftformat`, `.swiftlint.yml` | `make lint` |
| `ci` | GitHub Actions, PR 템플릿, dependabot | `.github/**` | YAML 문법, 참조하는 make 타깃·경로 존재 |
| `docs` | 문서 | `docs/**`, `README.md` | 링크·코드·경로가 실제와 일치 |
| `chore` | 하네스(Claude Code, git 훅) | `CLAUDE.md`, `.claude/**`, `.githooks/**` | `.claude/hooks` 는 입력 JSON 으로 직접 실행해 확인, `.githooks` 는 `make test-hooks` |

검증 항목 중 `make lint`·`make test`·`make test-hooks`·YAML·JSON 검사는 커밋마다 돌리지 않는다. `/micro-commit` 은 커밋만 하고, `/pr` 이 push 직전에 브랜치 마지막 커밋에서 한 번 돌린다 (`make test` 가 `make project` 를 포함한다). 커밋 뒤에 amend·rebase 를 해도 실제로 올릴 상태를 검사하기 위해서다. 이미 열린 PR 에 후속 커밋을 올릴 때도 `/pr` 로 push 한다 (원격 커밋을 덮어쓰는 push 는 §5 "덮어쓰기 push" 행대로 사용자가 직접 하고, 그 head 는 다음 `/pr` 이 검사한다). CI 는 `.claude/**` 만 바뀐 변경에서 lint·test 를 건너뛰고 settings.json 을 검사하지 않기 때문이다. 링크·경로 일치, Claude Code 훅(`.claude/hooks`) 직접 실행처럼 자동화되지 않은 확인은 구현할 때 한다.

- 커밋 하나 = 목적 하나. 요약에 "그리고"가 들어가면 나눈다. 모듈이 다른 변경(Core 값 타입과 Client Interface), 이동·추출 `refactor` 와 그 위의 `feat`, 목적이 다른 문서 행·절은 따로 커밋한다. 한 파일에 목적이 섞여 있어도 hunk 단위로 나눈다 (hunk 하나에 두 목적이 섞였거나, 새 파일이거나, 커밋될 내용 기준 lint 가 실패하면 한 커밋에 두고 `/micro-commit` 보고에 적는다).
- **의미 단위를 우선한다. 중간 커밋은 빌드가 깨질 수 있다.** 예를 들어 Client Interface + Fake 커밋 시점에는 Impl 소스가 없어 빌드되지 않을 수 있다. 중간 커밋을 빌드되게 맞추려고 여러 의미를 한 커밋에 합치지 않는다. 빌드·테스트가 보장되는 지점은 브랜치 마지막 커밋(`/pr` 이 검사)과 CI 를 통과한 머지 커밋뿐이다. 그래서 버그 원인은 `git bisect start --first-parent` 로 머지 커밋(PR) 단위로 찾고, 그 PR 안에서는 커밋 내용을 읽어 좁힌다 (중간 커밋은 bisect 대상이 아니다).
- 구현과 그 구현의 테스트는 같은 커밋에 넣는다 (테스트 없는 구현 커밋 금지).
- 순서는 의존 방향을 따른다 (빌드 보장이 아니라 읽는 순서를 위해): 도구·빌드 → 코드 → lint 설정 → CI → 문서 → 하네스. 단, `git mv` 로 이미 스테이지된 내용 그대로의 이동은 맨 앞에 한 커밋으로 따로 둔다 (역할은 새 경로 기준, `/micro-commit` 1단계).
- 기능 코드도 잘게 나눈다: Client Interface + Fake → Feature Model + 테스트 → View·Example → Impl + 테스트 → App 연결.

## 6. Claude Code 작업 방식
- 작업 시작 전 DEVELOPMENT_PLAN 의 해당 주차 목표와 이 문서들을 확인한다.
- 구조를 바꾸는 결정(새 외부 의존성, 모듈 종류 추가, 네트워크, 아키텍처 규칙 변경)은 먼저 제안하고 합의한 뒤 진행한다. 합의되면 이 문서와 ARCHITECTURE.md 를 같은 PR 에서 갱신한다.
- 작업 시작 전에 작업 범위를 정한다: In(이번에 다루는 흐름), Out(다루지 않는 것), 위협 모델(막는 대상이 실수인지 의도적 우회인지 같은 것. 있으면 한 줄), 수용 확인(끝났다고 판정할 실행 가능한 명령·절차). 팀 구현이면 설계자가 설계에 넣고, 혼자 하면 구현 전 계획에 적는다. 수용 확인은 구현한 쪽(팀이면 구현자)이 `/verify` 전에 실행하고 결과를 보고에 적는다 (수정 라운드마다 다시). 그중 §3 표가 테스트를 요구하는 앱 동작은 그 단위 테스트로, git 훅 동작(`.githooks`)은 `make test-hooks` 로 레포에 커밋해 `make test`·CI(필수 체크 `ci-result`)가 다시 돌리게 한다. 그 밖의 확인(문구 검색, `.claude/hooks` 직접 실행, 테스트를 일부러 망가뜨려 보는 확인 등)은 커밋하지 않아도 된다. 구조 결정을 제안할 때는 함께 보이고, 그 밖에는 완료 보고에 보인다 (사용자가 바꾸면 그것을 쓴다). 리더는 `/arch-review` 인자로, `/pr` 은 PR 본문 "범위" 절로 리뷰어에게 넘긴다. 문서 몇 줄 같은 작은 변경은 생략할 수 있다 (없으면 Out 이 없다, §5 "리뷰 기준").
- 구현을 시작하기 전에 바꿀 동작을 설명하는 문서를 먼저 찾는다. §5 "리뷰 기준"의 문서 범위를 식별자(타입·함수·스킬 이름)와 동작을 설명하는 문구(예: "PR 전에", "커밋마다")로 검색해 영향 문서 목록을 만들고, 코드와 같은 작업에서 고친다. 구현 중에는 `.claude/hooks/doc-refs.sh`(PostToolUse) 가 고친 파일의 경로·이름을 언급하는 문서 줄을 알려 준다.
- 문서의 규칙 한 줄을 고칠 때는 그 줄이 속한 `##` 절 전체를 읽고, 같은 주제를 다른 말로 설명하는 줄(표의 열 이름 포함)도 함께 맞춘다. 검색은 표현이 다르면 놓치기 때문이다. 파일 전체가 아니라 절 하나만 읽는다.
- 이 문서와 ARCHITECTURE 의 규칙(허용·금지, 정의, 심각도, 처리)은 스킬·CI 리뷰 프롬프트·완료 기준에 다시 적지 않고 절을 가리킨다. 그곳에는 절차만 적는다. CLAUDE.md("작업 흐름"·"반드시 지킬 것")와 DEVELOPMENT_PLAN "작업 진행 방식"은 요약이고 상세는 이 문서를 가리킨다. 규칙 줄을 고치면 그 규칙의 핵심 문구(예: "순수 로직")로 §5 "리뷰 기준"의 문서 범위를 검색해 다시 적은 줄을 맞추거나 참조로 바꾼다 (그 줄이 `.github/workflows/claude-review.yml` 에 있으면 CI 리뷰 갈음 PR, §5).
- 문서에 쓰는 사실 주장(CI 동작, 스크립트 동작 등)은 근거 파일을 열어 확인한 뒤 쓴다.
- 로컬 빌드·테스트는 자유롭게 실행한다 (`make test`).
- 역할 하나를 마칠 때마다 `/verify` → `/arch-review` 로 검증하고 멈춘다 (팀 구현이면 아래 "팀 구현" 흐름 끝까지 하고 멈춘다). **커밋(`/micro-commit`)과 PR(`/pr`)은 사용자가 지시할 때만** 실행한다.
- 처리를 정하지 않은 🔴 필수 지적을 남긴 채 커밋하거나 PR 을 만들지 않는다 (처리: §5 "리뷰 지적 처리").
- lint 오류를 `// swiftlint:disable` 로 숨기지 않는다.
- 사용자가 요청하지 않은 리팩터링이나 범위 확장은 하지 않는다. 발견한 문제는 보고한다.

### 팀 구현
리뷰 지적을 고친 곳에서 다시 지적이 나오는 반복을 막으려고, 설계와 검토를 구현 전에 하고 수정할 때도 같은 팀을 유지한다. 새 상태나 실패 경로가 생기는 구현(비동기 상태, 화면 상태, 저장 형식, 하네스 흐름)은 팀으로 한다. 문서 몇 줄·설정 같은 작은 변경은 위 흐름대로 혼자 한다. 어느 쪽인지 애매하면 사용자에게 묻는다.

"팀 역할"은 아래 표의 역할이다 (§5 마이크로 커밋의 커밋 역할과 다르다). 리더 밖의 팀 역할은 리더가 띄운 Agent Teams 팀원이다 (사용자 설정 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`). 팀원은 세션 내내 살아 있고 SendMessage 로 서로 직접 묻고 답하므로, 수정 라운드에서도 같은 팀원이 설계 맥락을 이어 간다. `/verify`·`/arch-review` 는 리더가 실행한다. 세션을 새로 열거나 `/resume` 하면 팀원이 복원되지 않으므로 같은 팀 역할로 새로 꾸린다. Agent Teams 가 꺼져 있으면 Agent 도구 서브에이전트로 대신하고, 수정 라운드에서는 SendMessage 로 같은 에이전트를 다시 부른다.

| 팀 역할 | 하는 일 |
|---|---|
| 리더 (메인 대화) | 작업을 나눠 맡기고, `/verify`·`/arch-review` 를 실행하고, 사용자 결정을 묻고, 결과를 보고한다. 직접 구현하지 않는다 |
| 설계자 | 구현 전에 설계를 낸다: 작업 범위(In/Out·위협 모델·수용 확인, 위 항목), 상태와 전이, await 지점별 취소·재진입·겹침·실패 경로와 그때 사용자에게 보이는 것, 영향 문서 목록(위 항목) |
| 비판자 | 설계와 수정 방식을 §5 "리뷰 기준"(작업 범위 포함)으로 검토한다. 🔴 가 없고 수용 확인이 실행할 수 있으면 통과이고(🟡 는 보고에 적는다), 통과해야 구현을 시작한다. 두 번 오가도 통과하지 못하면 리더가 쟁점을 사용자에게 묻는다 |
| 구현자 | 통과한 설계대로 코드와 테스트를 쓰고, 설계자의 영향 문서 목록에 있는 문서를 같은 작업에서 고친다. 여럿이면 파일이 겹치지 않게 나눈다 (예: Client Impl / Feature) |
| 대조자 | 수정 라운드에서 리더가 넘긴 `/arch-review` 결과와 전체 변경분을 지난 지적 목록(리더가 넘기는, 이 대화에서 고치기로 정한 지적. 보류·기각·범위 밖으로 정한 지적은 대조하지 않는다)과 대조해, 지난 지적이 같은 종류 전체로 고쳐졌는지 본다. 미흡은 같은 종류 중 §5 "리뷰 기준"으로 지금도 지적 대상(범위 밖이 아님)인 지점이 남은 경우다 |

비판자와 대조자의 판정은 처리를 정해 기록할 리뷰 지적(§5)이 아니라 다음 단계로 갈지(구현 시작, 다음 수정 라운드) 정하는 근거다. 대조자가 미흡하다고 판정하거나 `/arch-review` 에 새 지적이 나오면 리더는 멈추고 보고한다. 다음 수정 라운드는 사용자가 지시하거나(대조자 판정) 새 지적의 처리를 정한(§5) 뒤 시작한다.

흐름: 설계 → 비판 통과 → 구현 → `/verify` → `/arch-review` (대조자 대조는 지난 지적이 있는 수정 라운드에서만 한다). `/verify` 가 스스로 고친 것은 뒤의 `/arch-review` 가 전체 변경분에서 함께 보고, `/verify` 가 고치지 못한 실패는 구현자에게 돌려 고치되, 고치는 방식이 새 상태나 실패 경로를 만들면 설계자·비판자를 거친다. 리뷰 지적(로컬·CI)을 고칠 때도 같은 팀 역할로 이 순서를 다시 돈다.
1. 설계자가 지적과 같은 종류(같은 패턴의 다른 지점)를 §5 "리뷰 기준"의 범위 안에서 모두 찾는다. 범위 밖에서 찾은 지점은 고치지 않고 `범위 밖` 으로 보고한다 (처리는 §5 "리뷰 지적 처리").
2. 비판자가 수정 방식이 새 상태나 실패 경로를 만드는지 본다.
3. 구현자가 같은 종류를 한 번에 고친다.
4. `/verify` 뒤 `/arch-review` 로 고친 부분만이 아니라 전체 변경분을 다시 리뷰하고, 대조자가 지난 지적과 대조한다.

지적의 처리(반영·보류·기각·범위 밖)는 팀이 아니라 §5 "리뷰 지적 처리"대로 사용자가 정한다.
